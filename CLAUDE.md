# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

concord4pi bridges a Concord alarm panel's SuperBus 2000 (SB2000) Automation Module, connected over RS232 serial, to an MQTT broker. It publishes alarm state to MQTT topics and can optionally relay raw panel commands received over MQTT back to the panel. Plain Java, no framework. There's a JUnit 5 unit test suite in `test/` (see "Tests" below).

## Build and run

- Build: `ant` (default target `dist`). This compiles `src/concord4pi` against every jar in `lib/` into `build/`, then writes **`jars/concord4pi.jar`, a file tracked in git**. Rebuilding changes a committed artifact, so check whether the user wants the jar committed.
  - **Don't commit the jar that ant builds.** The committed `jars/concord4pi.jar` (last changed in `e1659f0`) is a ~1.3 MB jar that ant can't reproduce. It bundles Paho, tinylog and jSerialComm, has `Main-Class: concord4pi.concord4pi`, and is Java 17 bytecode. `startup/start.sh` depends on that, because it runs the jar with no other classpath. Ant's jar (~57 KB) has only the project classes and no `Main-Class`. After running `ant`, restore it with `git checkout -- jars/concord4pi.jar`. Docker is unaffected, because it rebuilds with ant and uses the full classpath.
- Clean: `ant clean`
- Language level: Java 21. The Docker image is `eclipse-temurin:21-jdk-alpine`, and it runs on an amd64 server. `build.xml` compiles with `release="${java.release}"` (21), so a jar built on a newer local JDK still runs in the image. If the base image changes, change `java.release` with it. The `openjdk` Docker images are deprecated, and the old `openjdk:15-jdk-alpine` tag no longer exists.
- For a quick compile without ant: `javac -d <outdir> -cp <lib jars> $(find src -name '*.java')`.
- Run from the repo root. `Config` reads the relative path `config/concord4pi.config`, and the app exits if `SerialDevice` is unset or the port can't be opened:
  ```
  java -Dtinylog.configuration=config/log.config -cp lib/jSerialComm-2.9.3.jar:jars/concord4pi.jar:lib/org.eclipse.paho.client.mqttv3-1.1.1.jar:lib/tinylog-api-2.6.0.jar:lib/tinylog-impl-2.6.0.jar concord4pi.concord4pi
  ```
  The ant build does not bundle the `lib/` jars into the output jar, so the full classpath is required. `startup/entrypoint.sh` uses this form. The classpath in the README, and `startup/start.sh` (jar only), are out of date.
- Docker: `docker build -t concord4pi .` builds with ant inside `eclipse-temurin:21-jdk-alpine` (amd64 and arm64 only), and uses `sed` to switch `config/log.config` from file to console logging. Ant rebuilds the jar inside the image layer, so a Docker build never dirties the committed `jars/concord4pi.jar`. To exercise the image without hardware, override the entrypoint and have `socat` make a pty inside the container (`socat PTY,link=/tmp/ser0,... PTY,link=/tmp/ser1,...`), point `SerialDevice` at one end and write frames to the other; `--add-host host.docker.internal:host-gateway` lets it reach a broker on the host. The JSON-form `ENTRYPOINT` and the `exec java` in `startup/entrypoint.sh` make the JVM PID 1, so `docker stop` delivers SIGTERM and `MainController`'s shutdown hook runs. Keep both.
- Without hardware: `debug/setupDebugSerial` uses `socat` to create a linked pseudo-serial pair (`debug/SERIALIN` / `debug/SERIALOUT`) with the SB2000 line settings (9600 8O1). Point `SerialDevice` at one end and write to the other.
- When upgrading a dependency in `lib/`, update the versioned jar names in `startup/entrypoint.sh` (and in the README).

## Tests

- Run: `ant test`. This compiles `test/` into `build-test/` and runs every test through the JUnit console launcher. A failing test fails the build. `ant` (dist) never runs or bundles tests.
- Layout: `test/` mirrors the package structure. JUnit 5.13.4 lives in `lib/test/` (kept on the 5.x line because JUnit 6 needs Java 17). The production `compile` only sees `lib/*.jar`. `test/tinylog.properties` keeps test logging at `error`.
- Helpers in `test/concord4pi/testsupport/`:
  - `RecordingBroadcaster`: captures every published topic and value. `RecordingBroadcaster.newAlarmSystem(recorder)` gives a wired-up `AlarmSystemData`.
  - `Messages`: builds valid frames with the length and checksum computed (`build`, `frame`, `frameWithBadChecksum`, `wire`).
  - `FakeSerialController`: records writes as `"ACK"`, `"NAK"` or the message text, without `MESSAGE_START`.
- **Known-bug convention:** each defect under "Known defects" has a test asserting the *correct* behavior, marked `@Disabled("Known bug: ...")`, so the suite stays green. When you fix a bug, delete its `@Disabled` line and the test becomes the check. When you find a new bug, add a disabled test the same way and list it under "Known defects". To confirm the disabled tests still fail, run the launcher with `--config=junit.jupiter.conditions.deactivate=org.junit.*DisabledCondition`.
- `SB2000ControllerTest` must be in package `concord4pi.SB2000`. It uses the package-private seams (see "Testability notes") and calls `processIncomingMessages()` / `processOutgoingMessages()` directly to step the run loop, without threads.
- `MessageProcessorTest` fixtures are built from the handlers' field offsets. `RealFramesTest` replays verbatim frames captured from the user's panel, which confirms those offsets on real data. Only non-identifying zone names are included, and no `09` frames. This panel reports its partition ID as `0100` (partition 1, area 0), not `0001`.
- Not covered: `MQTTService`, `MainController`, `concord4pi`, real serial I/O, and thread timing.

## Architecture

The work is split across three threads that communicate only through concurrent queues. They no longer poll in lockstep 50ms loops (see "Performance notes"): the serial thread waits on a monitor, the MQTT thread blocks on its queue, and the main loop sleeps only when a pass found nothing to do.

1. **`SB2000Controller`** (`src/concord4pi/SB2000/`): owns the serial port through `SerialController`. A jSerialComm data listener appends raw bytes to a `StringBuilder`, guarded by a semaphore; the run loop scans that buffer in place with a cursor (`requeueFrom` handles the partial-frame paths). The run loop frames messages: `MESSAGE_START`, then a 2-hex-char length, then the payload and checksum, all ASCII hex. It ACKs or NAKs each frame and pushes valid `IOMessage`s onto `rxQueue`. Outgoing `IOMessage`s go to `txVerifyQueue` until the panel ACKs them, and are retransmitted on NAK up to `maxReTransmit`. A `ControlMessage` is a single ACK/NAK byte. The run loop waits on the `workSignal` monitor (500ms fallback); `appendReceivedData`, `sendMessage` and `shutdown()` signal it, and it skips the wait while `txQueue` is non-empty.
2. **`MainController`** (main thread): drains `rxQueue` into `MessageProcessor`, collects inbound commands from every `IBroadcaster`, and queues any replies or commands back to `SB2000Controller`. At startup it sends `FULLCOMMAND_FullEquipmentList` so the panel reports all zones and partitions.
3. **Broadcasters** (`src/concord4pi/messaging/`, implementing `IBroadcaster`): `MQTTService` is currently the only one, and it is enabled by `MQTTBroadcaster=true`. Each broadcaster runs in its own thread and publishes queued `NotificationPacket`s. If `MQTTEnableCommands=true`, messages arriving on `<MQTTBaseTopic>/<MQTTCommandTopic>` are parsed as raw SB2000 hex commands, and a receipt is published under `<base>/<cmd>/receipt/{text,code,message}`. To add an output channel (the README mentions a REST API), implement `IBroadcaster` and register it in `MainController.addBroadcasters()`.

**Message dispatch:** `MessageProcessor.processMessage` calls `dispatchMessage`, which switches on `IOMessage.getCommandCodeString()` against the `COMMANDCODE_*` constants in `SB2000Constants`. That class holds all protocol constants: command codes, zone, siren and trouble codes, and their text names. Codes starting with `0x22` or `0x23` are two-byte commands (see `IOMessage.MULTIBYTECOMMAND_PREFIX`). Each handler slices fields out of `getDataString()` by character offset (2 hex chars per byte). Text fields are sequences of 2-char tokens that are decoded through `SB2000Constants.convertTextToken`. `processMessage` catches any `RuntimeException` from a handler (the offsets assume a full-length payload, so a short one throws), logs the frame at WARN and drops it, so one bad frame can't end `MainController`'s loop. State the handler set before it threw stays set.

**`IOMessage` format:** the constructor takes **ASCII hex bytes**, not binary. For example, `new IOMessage("020204".getBytes())` gives length `02`, command `02`, no data, and checksum `04`. The ASCII hex string excludes the leading `MESSAGE_START` (`0x0A`) and includes the trailing checksum. The length byte counts itself, the command, and the data, but not the checksum. The checksum is the low byte of the sum of the length, command, and data bytes. `test/concord4pi/testsupport/Messages` builds valid frames from a command and data. `isValid()` checks both the declared length and the checksum. Most malformed input (odd length, non-hex, wrong length) doesn't throw, including a length byte of `00`: it produces an invalid message with an empty command code. `getMessageBytes()` is an unimplemented stub that returns `null`. `toString()`, `getCommandCodeString()` and `getDataString()` are built on first use and cached (fixed on the `perf-improvements` branch), which is safe only because the fields are set in `initMessage` and the byte arrays never escape the class — adding a setter to `IOMessage`, or handing out `getData()`/`getCommandCode()` to something that mutates them, would make the caches stale.

**State model and MQTT topics** (`src/concord4pi/data/`): `AlarmSystemData` is the root. It has an `AlarmPanel` and creates `AlarmAreaPartition`s lazily (`getAreaPartitionByID`) as the panel reports them. Partitions in turn own zones, touchpads, users, sirens, arming level, troubles, and so on. Every node implements `IAlarmObject`:
- `myAddress()` returns `parent.myAddress() + "/<segment>/" + ID`. This path becomes the MQTT topic suffix. IDs are the raw 4-hex-char strings from the panel, e.g. `/partitionarea/0001/zones/0005/status`. `MQTTService` publishes to `MQTTBaseTopic + suffix` with no separator added, because the suffix already starts with `/`.
- Setters call `updateTrigger(new NotificationPacket(myAddress() + "/field", value, action))`. The packet bubbles up through the parents to `AlarmSystemData.updateTrigger`, which hands it to every broadcaster. `MQTTService` skips `NPACTION_NEW` packets that have empty values. Every constructor fires one of these empty `NEW` packets.
- Lookups like `getZoneByID` and `getUser` **create** the child if it's missing, so a lookup on a mistyped ID silently adds a new node.
- The model has no hardware or network dependency. Construct `AlarmSystemData` with a stub `IBroadcaster` that records the packets, and you can drive it directly or through `MessageProcessor`. This is the easiest place to observe behavior.
- Naming convention: topics and log text say "partitionarea" (issue #7), even though the class is still named `AlarmAreaPartition`.
- History lists (zone text, partition text, key fob commands, trouble events, siren sync events) keep the newest five, newest at index 0, so `getText()`, `getMostRecent*()` and `getPast*(0)` return the latest. An index past the end returns `""`, `null`, or `-1` for a key fob command (text `NONE`) instead of throwing.
- Arming-level delay flags, confirmed on real panel traffic: bits 4-5 are the delay length (`0x10` extended, `0x20` twice extended, `0x30` reported as `UNKNOWN`), bit 6 (`0x40`) is exit delay, and bit 7 (`0x80`) is end of delay, e.g. `0xC0` when an exit delay finishes. The number goes to `/armingLevel/delayFlags` and the text to `/armingLevel/delayFlags/text`.

## Testability notes

- `LogEngine` ignores its `Config` argument, so `new LogEngine(null)` works. If tinylog has no configuration, it logs everything to the console at trace level. Pass `-Dtinylog.writer.level=error` (or supply a config) to quiet it.
- `SerialController`'s public constructor opens the real port and calls `System.exit(0)` on failure. `MQTTService`'s constructor connects to the broker and also exits if it can't create the client.
- Seams added for tests. Keep them, and keep them free of behavior changes:
  - `SerialController(LogEngine)` (protected): doesn't open a port.
  - `SB2000Controller(SerialController, LogEngine)` (package-private): the public constructor delegates to it.
  - `SB2000Controller.appendReceivedData(byte[])` (package-private): the serial listener calls it.
  - `processIncomingMessages()` and `processOutgoingMessages()` (package-private).
  - `Config(String configFileName)`: the no-argument constructor uses `config/concord4pi.config`.
- `Config`'s `Properties` field is `static`, so each new `Config` replaces the values that every instance sees.
- Several failure paths call `System.exit(0)`, so the process reports success even when startup fails.

## Known defects (verified 2026-10-23; remove entries as they're fixed)

Don't write tests or code that rely on these behaviors as if they were correct.
- **`AlarmTemperature.myAddress()`** uses `parent.getID()` instead of `parent.myAddress()`, which produces the topic `0001/temperature` (no leading `/` and no `partitionarea`).
- **`AlarmArmingLevel.isArmed()`** is inverted: it returns true for level ≤ 1 (Zone Test or Off). It has no callers yet.
- **`AlarmAreaPartition.isArea()` / `isPartition()`** parse the hex ID halves with radix 10, so an ID containing A–F (for example `000A`) throws a `NumberFormatException`. `isArea()` runs every time arming-level text is built.
- **Unhandled command codes.** The panel sends these, but `MessageProcessor` has no `case` for them, so each one logs `Received Message ... without handler` at WARN and is otherwise ignored. They're mostly answers to the startup equipment-list request. In a real capture (2026-10-23), the frames were `05` ×6, `06` ×9, `07` ×6, `08` ×1, `09` ×3, `0A` ×16, `0C` ×6 and `2301` ×12. Per the SB2000 automation protocol (names from memory, so check against the protocol document before implementing), they are:
  - `05` SuperBus device data (constant `COMMANDCODE_SELSUPERBUSDEVICE` exists)
  - `06` SuperBus device capabilities
  - `07` output data
  - `08` equipment list complete
  - `09` user data
  - `0A` schedule data
  - `0C` light-to-sensor attachment
  - `2301` lights state (constant `COMMANDCODE_LIGHTSSTATE` exists)

  `RealFramesTest.UNHANDLED` holds one real example of each code except `09`.
- **`09` user data appears to contain user codes (PINs) in plain BCD**, including the system master and installer codes. Never commit `09` frames, and never publish those bytes to MQTT if a handler is ever added. Treat debug logs as sensitive, because `SB2000Controller` logs every raw frame at DEBUG. Above DEBUG, log a frame with `IOMessage.getSummary()` (command code and data length, no bytes), never `toString()`, unless the handler only ever sees a command that can't carry codes. Outgoing `40` keypress commands sent over MQTT can carry a PIN too. Until 2026-10-24 the "without handler" WARN logged every `09` frame in full at the production level, so older logs from a deployment may hold the panel's codes.
- **Text tokens:** word tokens (such as `6E` FRONT and `57` DOOR) are concatenated with no space, which gives `FRONTDOOR`. The panel separates letter tokens with an explicit space token (`2B`), but not word tokens. Tokens `FB` and `FE` have no mapping and decode to `""`. In touchpad text, `FB` appears to separate the two display lines, so `*FRI OCT 23` and `03:40 PM P1` run together as `...2303:40...`.
- **`MessageProcessor.partitionData`** (command `04`) decodes the partition's text tokens and then discards them. The text is never stored or published, which looks unfinished.
- **`MessageProcessor.timeAndDate`** passes the panel's 1-based month to `Calendar` (which is 0-based) and the 2-digit year as is.
- **`SB2000Controller` framing:** if leading bytes aren't `MESSAGE_START`, ACK, or NAK, the whole buffer is requeued, and processing waits until more serial data arrives. The leading garbage is then framed as a message and NAKed. Every pending `IOMessage` is written immediately, without waiting for each ACK. ACKs and NAKs are matched to `txVerifyQueue` by order alone.
- **`SerialController.setupSerialPort()`**: a malformed `SerialDevice` value (such as the placeholder in the committed config) makes `SerialPort.getCommPort` throw an uncaught `SerialPortInvalidPortException`, so the friendly "could not be opened" message is never shown.
- **Shutdown runs twice:** on SIGTERM, the `appTerminator` shutdown hook calls `MainController.shutdown()` and sets `isRunning = false`. The main loop then exits, and `concord4pi.go()` calls `shutdown()` again, possibly at the same time as the hook. Whether you see the second one is a race — it depends on whether the main thread gets there before the JVM finishes exiting. Measured with `docker stop` (2026-10-24): the HEAD image logged "Serial Port ... CLOSED!" twice in 1 of 3 runs, this branch twice in 3 of 3 (its shutdown window is ~0.5s longer because the MQTT run thread blocks up to 500ms on its queue poll). Harmless either way, because the second close succeeds.
- **`MainController.addBroadcasters()`** calls `.equals` on `MQTTBroadcaster` and `MQTTEnableCommands` without a null check. A missing key causes an NPE.
- **MQTT never retries the initial connection.** Paho arms automatic reconnect only from `connectionLost`, so it needs a connection that succeeded at least once. If the broker is down when `MQTTService` is constructed, `connect()` throws, logs "Could not connect to MQTT Broker... Disabling service!" at WARN, and returns false. `isRunning` stays false, the run thread exits on its first loop check, and MQTT is dead for the life of the process. Easy to hit when the bridge and the broker start together and the broker loses the race.
- **A disabled `MQTTService` still accumulates notifications.** `addBroadcasters()` registers the broadcaster whether or not it connected, and `sendNotification` has no `isRunning` guard, so `AlarmSystemData.updateTrigger` keeps calling `notificationQueue.offer(...)` with nothing draining it. The queue grows unbounded for the life of the process (heap growth, then GC pressure). Only reachable through the defect above, so a deployment whose broker is up at startup won't see it.
- **No resubscribe after an automatic reconnect.** `connect()` leaves clean session at Paho's default (`CLEAN_SESSION_DEFAULT = true`), so the broker discards the subscriptions when the connection drops, and Paho 1.1.1's internal `connectComplete` is a no-op that does not resubscribe. `startListening()` runs once, in the constructor. After any broker restart, outbound publishing recovers normally while inbound commands on `<base>/<cmd>` are silently dead until the process restarts — so the service looks healthy while `MQTTEnableCommands` no longer works. `MqttCallbackExtended` is present in 1.1.1, so having `MQTTMessageHandler` implement it and call `startListening()` from `connectComplete` fixes this without upgrading the jar.
- **MQTT failures log at TRACE.** `startListening()`, `stopListening()` and every `publish()` failure in `sendMessage` log at TRACE, invisible at the default `info` level. Offline buffering is also off (`DisconnectedBufferOptions` is never set; its enabled and persist defaults are both false), so state updates published during a broker outage are discarded with no visible trace.

## Performance notes (current branch is `perf-improvements`)

All four groups of findings in `specs/performance-improvements.md` are fixed on this branch (measured end to end against the pre-change build, real broker, log level `info`): idle 1.02% → 0.85% of a core, a sustained 10 frames/second 9.78% → 4.27% for identical work, and at 50 frames/second the old code could only drain ~17/s (its `MainController` ceiling) while this one keeps up at ~46/s. Behavior is unchanged — verified by diffing 445 serial byte streams and 955 `IOMessage` inputs against the old build.

- ~~`LogEngine.log` walks the stack twice per call before tinylog filters by level.~~ Fixed on this branch: `LogEngine` checks `isEnabled(level)` first and returns, then resolves the caller once with `StackWalker`. There is a lazy `log(Supplier<String>, Level)` overload, and the TRACE/DEBUG call sites in `SB2000Controller`, `SerialController` and `MQTTService` use it, so their message strings aren't built when the level is off. Use it (or the package-private `isEnabled(Level)` guard) for any new TRACE/DEBUG call whose message is built by concatenation. The data model deliberately still builds its TRACE strings eagerly — those setters run a few times per frame, so converting them measured as noise. Because building is deferred, `LogEngine` contains a `RuntimeException` thrown while building a message and logs `<log message could not be built: ...>`, so a getter that throws (several do — see "Known defects") can't crash the caller, and can't do it only at one log level.
- Thread waiting is fixed on this branch: `SB2000Controller` waits on a monitor (500ms fallback), `MQTTService` blocks on a `LinkedBlockingQueue` with a 500ms poll, and `MainController` sleeps 50ms only after an idle pass — it now drains the whole rx queue per pass instead of one message. The `MQTTService.shutdown()` and `SerialController.closePort()` busy-spins are gone too (50ms poll, 5s timeout, then WARN and continue). `MainController`'s idle sleep is the only fixed-interval wakeup left.
- ~~The serial receive buffer is a `String` concatenated on every serial event and re-sliced per frame.~~ Fixed on this branch: it's a `StringBuilder` scanned in place with a cursor index, so the cost is linear in the bytes received instead of quadratic in the burst size. Framing semantics are unchanged — verified by diffing a 445-stream transcript against the pre-change build.
- ~~The README says MQTT client persistence is disabled, but `MQTTService` still uses `MqttDefaultFilePersistence("/tmp/concord4pi")`.~~ Fixed on this branch: `MQTTService` uses `MemoryPersistence`, so there's no disk write per publish and no `/tmp/concord4pi`. The README's v0.3 changelog still mentions that directory; it's historical, not current behavior. Publishes stay at QoS 1 (asked and confirmed 2026-10-24), and the production container runs at log level `info`.
- ~~`IOMessage` round-trips through a regex split on construction and rebuilds its hex string with `String.format` per byte on every `toString()`.~~ Fixed on this branch: the regex and per-pair substrings are gone (`Integer.parseInt` on the CharSequence, which also preserves its quirks — `+5` parses as length 5, `-1` as `FF`), formatting uses a nibble lookup, and the three derived strings are cached. `MessageProcessor`'s per-frame cost went from ~18 µs/48 KB to ~0.5 µs/0.7 KB.

## Configuration

- `config/concord4pi.config` is a Java properties file read by `Config`. The README lists the keys. `Config.getProperty` can return `null`, and `MainController.addBroadcasters()` calls `.equals` directly on the `MQTT*` values, so a missing key can cause an NPE.
- `config/log.config` configures tinylog. `writer.level` is one of error/warn/info/debug/trace, and the system property `-Dtinylog.configuration` points to this file. There's no global `level` key, so `writer.level` is what `LogEngine.isEnabled` reports. Log calls go through `LogEngine.log(msg, Level)` or `log(() -> msg, Level)`.
